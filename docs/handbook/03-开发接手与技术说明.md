# AI WorkHub 开发接手与技术说明
2026年11月10日　面向接手开发与测试人员　基线 a1fa1f7

先区分运行模式，再阅读业务服务。项目为 React 单页前端与 Spring Boot 服务，SQLite 保存本地数据。客户工作流与采购各有版本聚合，服务端权限和状态校验才是正式边界。仓库原始 V2 文档与 V3 历史记录保留，但不能代替本次基线说明。

## 1 版本和目录
当前 backend/pom.xml 为 3.2.0，frontend/package.json 为 3.1.0；不要根据旧 README 的 3.1.0 jar 名启动新后端。当前基线完整提交号为 a1fa1f7c1c950eaf27ea2b0b84580884e24fba60。

位置｜职责｜接手时注意
frontend/src/api.ts 与 realApi.ts｜构建时选择模拟或真实 API｜VITE_DEMO_MODE 是构建开关，不是登录选项
frontend/src/demo｜工作台浏览器模拟接口｜不要当作正式权限校验
frontend/src/workflow｜工作区、知识修订、共享企业配置｜profiles.json 同时打入后端资源

技术基线为 React 18、TypeScript 5、Vite 5、原生 CSS；Java 8 兼容源码、Spring Boot 2.7.18、JdbcTemplate、SQLite。便携包曾采用 Java 17 运行时，这不代表源码已迁移到 Boot 3。未来升级依赖前单独评估兼容与支持周期，本文件不声称这些版本适合长期公网运行。

## 2 数据与并发
传统表包括 tenants、users、memberships、sessions、cases、products、reviews、audit_logs。case_workflows 保存工单 JSON 与 revision，case_access 记录关联访问；knowledge_versions 保存独立知识版本；procurement_projects 保存采购 JSON、tenant_id 与 revision。

版本命令携带当前 revision，更新语句同时匹配旧 revision，冲突返回 REVISION_CONFLICT。前端应保留用户输入并重载比较，不能用盲重试覆盖新数据。SQLite 连接池固定为一，适合单机小规模；不要未经验证开启多个程序实例共用数据目录。

## 3 核心接口索引
接口｜用途与关键参数
POST /api/auth/login｜登录；返回服务端会话
POST /api/auth/switch-tenant｜仅切换有成员关系的企业
GET /api/workflow/profile 与 members｜企业配置与成员
GET /api/workflow/inbox｜当前用户待办与待审
GET 或 POST /api/cases/{id}/workflow｜读取或提交 op 与 revision
GET 或 POST /api/knowledge/{id}/versions｜知识历史与修订
POST /api/knowledge/{id}/versions/{version}/publish｜非作者发布审核
POST /api/knowledge/{id}/retire｜撤回资料
GET 或 POST /api/procurement｜采购列表与创建
POST /api/procurement/{id}｜op 加 revision 的采购命令
GET /api/procurement/{id}/comparison｜关闭且必要同步完成后的比价
POST /api/procurement/{id}/sync｜采购端主动同步
GET 或 POST /api/supplier/{id}｜通过 X-Invitation 限定本家数据
POST /api/procurement-relay/{id}｜X-Relay-Key 校验的门户收件同步

工单命令包括 fields、evidence、draft、submit、approve、reject、copy、dispatch、task、taskComplete、taskCancel、assign、status、close、reopen。具体字段以 WorkflowService.command 为准；不得通过旧工单状态接口绕过结案检查。

采购命令包括 invite、close、offer、award、change、approveChange、withdraw、complete。报价提交使用 requestId 去重；金额以字符串传输，后端 BigDecimal、前端 BigInt 分币，不能使用浮点数累计钱款。

邀请链接秘密在 fragment 内，通过 X-Invitation 请求头使用；门户共享密钥只配置在服务端。接口示例和错误日志不得记录秘密、完整邀请链接或用户会话。角色权限检查既在请求边界也在业务服务内，不能因新增移动页面放宽。

## 4 优先任务与已知差异
先为真实后端增加完成、退出、变更、已承接后议价的转换拒绝测试，再改服务逻辑。同步网络调用当前处于事务路径，应拆为 outbox，避免阻塞单连接。统计接口与前端 supplierData 的时间分母应统一，当前不要擅自对历史指标做无说明重算。

## 5 开发与构建步骤
开发环境需要可用 JDK、Maven、Node 与 npm，无须独立安装数据库。实际工具版本以项目锁文件与构建成功记录为准；CI 当前采用 Node 20。首次联网准备依赖，离线打包的 mvn -o 只在依赖已缓存时可用。

后端终端在 D:\AI-tools\backend 执行 mvn test，再执行 mvn package。产物为 target\workhub-backend-3.2.0.jar。独立测试库启动示例：
java -jar target\workhub-backend-3.2.0.jar --server.port=18080 --spring.datasource.url=jdbc:sqlite:data/workhub-preview.db

前端终端在 D:\AI-tools\frontend 执行 npm ci。开发时设置 $env:VITE_API_TARGET='http://127.0.0.1:18080'，再运行 npm run dev。检查 vite.config.ts 中实际代理配置，不在页面中硬编码后端端口。

真实包构建前在同一 PowerShell 明确设置 $env:VITE_DEMO_MODE='false' 和 $env:VITE_BASE='/'，再 npm run build。随后打包后端，因为 Maven 会把 ../frontend/dist 复制进 static。先打后端再改前端会把旧页面装入 jar。

Pages 构建使用 $env:VITE_DEMO_MODE='true' 和 $env:VITE_BASE='/AI-tools/'，再 npm run build。推送 main 触发 .github/workflows/deploy-pages.yml。发布成功后仍须核对线上 JS 文件哈希及交互，不能只看 push 成功。不得将 Pages dist 误打入本地正式包。

## 7 数据迁移和安全接手
新增字段先确定 JSON schema_version、默认值和旧聚合读取策略。迁移必须有旧库备份、幂等升级脚本和失败回滚；不要删旧库重建来验证升级。供应商名称迁移为稳定 ID 时，人工确认映射，保持历史金额、版本和当时名称不变。

本地库含演示账号，正式交付需新增首次管理员初始化、改密和种子数据隔离。会话存数据库且 12 小时有效，退出撤销；成员停用和工作移交 UI 尚未完善。公开门户必须启用 portal-mode，不能把默认内部服务直接暴露公网。

对接客户工单与采购时，保存双向关联但不共享全部字段。客户回复只能引用明确授权的需求和结论，不带内部采购成本、其他供应商报价或内部审计。工单访问授权与企业成员资格是两层条件，不可合并成简单企业管理员万能权限。

## 8 变更提交约定
一个提交围绕一个可验收业务变化，变更前列出受影响模式、接口、状态转换与数据版本。新增页面必须检查真实服务及演示两种模式，移动端检查输入、长名称、空状态和错误恢复。更新 Word 源 Markdown、业务说明及测试后，再说明验证范围。

提交前依次检查 git diff --check、前端规则测试和构建；涉及后端则 mvn test 与 package；涉及打包则新目录启动和停服；涉及门户则隔离边界、重复回执、失败重试和最终收齐。不要提交数据库、运行时、node_modules、target、密钥或用户导出。
