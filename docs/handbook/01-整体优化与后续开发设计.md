# AI WorkHub 整体优化与后续开发设计
2026年11月10日　产品与开发评审版　基线 a1fa1f7

本方案供项目负责人、业务负责人和后续开发者使用。建议先把已有业务闭环做可靠，再增加自动化：优先统一演示与本地版行为、补齐采购状态约束、供应商主档和数据备份，然后开展三企业试点。真实模型、渠道集成和三维产品展示排在验证业务收益之后。本文件提出的迭代均为待开发，不代表本轮已经实现。

## 1 当前平台能做什么
已实现：企业登录与角色隔离、三企业场景配置、客户需求确认、知识版本引用、回复审核和发送登记、跟进任务、结案重开；采购侧包括邀请链接、报价、比价、反向议价、承接、变更、统计台账及供应商档案。页面中的发送登记是记录外部实际发送，平台没有自动发送邮件或 WhatsApp。

存在三种运行形态：GitHub Pages 是浏览器本地模拟；本地完整服务使用 SQLite；公网供应商门户是独立服务方案，已有同步代码但没有完成公开部署验收。Pages 的按钮可演示完整流程，不能据此判断公网采购已上线。

## 2 整体业务优化顺序
优先级｜业务问题｜建议结果
P0｜本地版和演示版的约束、交互不完全相同｜先以真实后端为准建立共同验收场景，再复用表单和状态展示
P0｜数据放在本机，缺少可验证恢复流程｜提供一致性备份、恢复预检和升级回滚，完成干净电脑验收
P1｜同一家供应商按名字归集，别名和同名会影响评价｜引入企业内稳定供应商编号，保留名称快照与合并记录
P1｜工单与采购是两个入口，业务人员重复抄需求｜通过关联编号连接客户需求与采购，授权后带入已确认字段
P1｜知识、规则、模板靠代码维护，更新影响在途工单｜建立版本发布、有效期及显式迁移机制
P2｜AI 和外部渠道尚未接入｜先测量人工基线，再以辅助草稿方式接入，保留人工承诺确认

目前已经有价值的能力是同口径比价、版本留痕、需求确认和授权审核。不应把自动分项最低价称为已成交价，也不应将供应商接受率包装成综合信用分。三企业真实产品、库存、订单、退款与成交收益数据尚未接入，不提供虚构经营结论。

## 3 采购可靠性迭代
第一批任务 PRC 01 是统一状态机。建议公开状态为草稿、收集中、已截止、议价中、已承接、履约中、已完成、已退出、已取消；状态转换集中在后端校验，演示调用同一规则契约。数据库仍可保留 status 与业务事实分开存储，但展示状态只能由一个映射函数派生。

现有后端需要优先补齐的约束：完成或退出后仍可能发起或批准费用变更；已完成后仍可登记退出；完成未强制拦截待确认变更；已承接后目标价与供应商回复缺少统一冻结条件。演示 reducer 对其中多项已有拦截，后端必须逐项补齐并增加直接调用 API 的拒绝测试。此处是代码核查发现，不代表已修复。

第二批任务 PRC 02 是需求改版。已发布原版本冻结，修改路线、货量、范围或费用科目时创建新版本并说明原因；旧报价和旧接受不得自动沿用。供应商需看到差异，重新明确接受。取消、撤销邀请、重发链接和报价撤回均形成独立事件。

第三批任务 PRC 03 是比价口径。费用项增加单位、数量、税费、包含项、有效期和可拆分标识。跨币种或税费不同不能直接取最小值。不可拆分包组按整组比较；缺项不是零；有条件报价必须核实后转为新报价版本，不能删除条件后冒用原承诺。

最低参考组合只是一轮询价的采购目标建议。即使低于所有整单报价，也可能没人接受；不得把参考与最低整单之差计作已实现节省。后续若展示节省，必须登记同范围预算基线、获选承诺价及结算口径。

验收要求：所有非法状态从 API、重复提交、旧版本、离线重试四个入口均被阻止；拒绝行为不改金额或承接记录；旧目标价接受不能承接新版本；每次允许的变更都保留操作者、时间、前后版本与依据。

## 4 本地数据与联网同步设计
保留本地 SQLite 作为采购方主数据存储，在线门户只持有供应商所需发布快照及回执。本地断网时仍可查看资料和编制草稿，但不能宣称已经发出或已经收到全部报价。供应商跨设备扫码仍需要网络和公开可达门户。

建议新增同步任务表 sync_jobs，字段包括 job_id、project_id、publication_version、request_id、status、attempts、next_retry_at、last_error；建立本地 outbox 与门户回执游标。任务在业务事务内创建，后台执行网络请求，不长期占用 SQLite 单连接事务。网络失败只改变同步状态，不回退已保存的业务草稿。

门户按 request_id 去重，发布版本单调前进，旧版本不能覆盖新版本；回执分页拉取并由本地校验项目、邀请和版本后入库。界面显示待同步、发送中、已收件、失败待重试及最近成功时间。关闭后先完成最终同步，再允许正式比价。退避重试、人工重试和异常恢复均使用同一任务编号。

建议新增 supplier 主档、supplier_alias、procurement_round、invitation、quote_version、target_offer、offer_response、award、change_request、business_event 等实体。第一阶段可继续使用 JSON 聚合，不要求一次重写所有存储；先做 schema_version 与可回滚迁移，再按查询和约束需求拆表。

供应商主档按 tenant_id 加 supplier_id 隔离，名称只用于展示。历史同名项目先进入待确认匹配列表，不自动合并；人工合并保留旧编号、理由和操作者。已出具报价保留当时名称与资质快照。

备份建议采用停服一致性备份或 SQLite 在线备份 API，连同版本清单和校验值保存；密钥配置另行加密保管。恢复先在临时目录校验结构与版本，再关闭服务替换，保留旧副本用于回滚。不可把设置页业务 JSON 导出称为全库备份。

## 5 三企业与日常工作优化
Kotech 优先优化压力和气量的单位及测量基准、供电条件、型号与序列号、技术资料版本。型号推荐只提供候选和依据；技术承诺必须有资料及审核人。备件图纸热点属于后续增强，需真实授权图纸，不用通用示意图代替型号适配。

Warmpaca 优先统一 SKU 与颜色尺寸、包装、可售核验时间、期望到达日和外部订单编号。没有库存接口时，把核验人、来源和时间做成可复用记录；过期后提示重新核查。售后受理与实际退款分开，平台不应把受理完成当作退款完成。

上海安特瑞商贸有限公司保留暂按润滑油贸易配置的状态，主营产品和授权仍须企业确认。优先收集指定产品、包装、数量单位、交付地区、税运费口径和有效期；替代产品必须有有效技术依据，禁止只凭相似品名推荐可替代。

共性优化是把客户需求、资料核验、承诺审核和跟进任务串起来。工单可关联采购项目，但仅传递授权后的结构化需求；采购成本、其他供应商报价和内部原因不自动进入客户回复。负责人变更需移交待办，审核和任务结束后应复核关联访问权限。

## 6 迭代里程碑与退出条件
阶段｜主要交付｜进入下一阶段的条件
R1 可靠性｜后端状态约束、共享规则测试、备份恢复、构建模式检查｜非法转换全部拒绝；恢复演练成功；真实版与演示版差异有清单
R2 数据闭环｜供应商编号、需求版本、可靠同步、成员移交｜两台电脑与手机可实测收件；重试不重复；改版须重新确认
R3 业务试点｜三企业脱敏样本、模板管理、时间和质量指标｜每企业至少完成一组代表性端到端场景并由负责人签认
R4 辅助智能｜资料提取、来源引用、差异提示、可选模型适配｜人工基线、成本预算与正确性抽查达标；人工审批仍有效

R1 至 R4 是建议顺序，不是已承诺工期。每阶段拆成可独立验收的小任务，先确定责任人与脱敏样本，再估工。不要同时引入多币种、复杂分包和自动下单。

试点记录人工重复录入次数、完成时长、报价回收率、目标价接受率、承接后退出率与变更原因。先积累分母和事件，样本不足时展示原始计数；不以单轮最低参考价作为业务收益。
